Caso 14512 · IM-918826-5-14512 Portal Vivanto — Caracterización OFFLINE

Por qué se detuvo la carga OFFLINE

La cadena que lleva las encuestas capturadas sin conexión desde el FTP hasta las tablas de caracterización está cortada desde el 16 de agosto de 2026. Este documento identifica el eslabón exacto, muestra el error que devuelve todas las noches, explica con detalle qué hace ese proceso, y separa lo que se puede reparar hoy de lo que exige una decisión de fondo. Incluye además la validación del informe del 12 de agosto sobre la transferencia entre servidores.

Hallazgo principal

El proceso que toma los JSON de /EncuestasACargar1 y los carga a la base existe, es automático y funcionó hasta el 14 de agosto. Desde el 16 de agosto falla todas las noches en menos de cuatro segundos con ORA-29283: la ruta de acceso o el archivo no existen.

No es un paso manual pendiente, no depende de que alguien lo ejecute, y no es el job que aparece deshabilitado desde 2024. Es un job encendido, en otro servidor, que perdió acceso a su carpeta de trabajo tras un reinicio de la base.

Dos jobs con el mismo nombre en dos servidores

El origen de la confusión es concreto y fácil de reproducir: JOB_PCD_FN_FTP_PC_IJ existe en los dos servidores, con nombre idéntico y comportamiento opuesto.

Qué hace exactamente el proceso que falla

PCD_FN_FTP_PC_IJ son once líneas que encadenan tres operaciones muy distintas. Conviene leerlas completas, porque cada una tiene su propio modo de fallar.

RNIENTREVISTA.PCD_FN_FTP_PC_IJ — en el 65
PROCEDURE PCD_FN_FTP_PC_IJ AS

RSULTADO VARCHAR2(500);
begin
    -- Call the function
    RSULTADO := FN_EXEC_FTP_JSFULL_WRAP('PRUEBA');   ← paso 1: FTP → disco
    dbms_output.put_line(RSULTADO);                 ← el resultado nunca se verifica
    insertar_json ;                                 ← paso 2: disco → DATA_JSON
    -- Call the procedure
    SAVE_SUPPORTS;                                  ← paso 3: soportes
end;

Paso 1 — Descargar del FTP al disco del 65

FN_EXEC_FTP_JSFULL_WRAP no es PL/SQL: es una envoltura sobre una clase Java cargada dentro de la base. Su cuerpo es una sola línea activa, con las alternativas históricas comentadas encima.

RNIENTREVISTA.FN_EXEC_FTP_JSFULL_WRAP
FUNCTION FN_EXEC_FTP_JSFULL_WRAP (NOMBRE NVARCHAR2)
RETURN VARCHAR2 AS LANGUAGE JAVA NAME
--'FTPJS1.ftp.iniciarProceso(...)'; -- descargar de ftp y cargar en db
  'pkgFTPdowloadfiles.ftp.iniciarProceso(...)'; -- solo descargar de ftp al server

La clase que queda activa es pkgFTPdowloadfiles, cuyo fuente Java (FTPDOWLOADFILES, 545 líneas) declara la carpeta remota sin ambigüedad:

FTPDOWLOADFILES — línea 85
String remotePath = "/EncuestasACargar1";

Es la carpeta correcta: la misma en la que se depositan los archivos manualmente. El Java se conecta a ftp.unidadvictimas.gov.co, lista ese directorio, descarga los archivos a F:\Encuestas en el 65 y deja allí un índice llamado nombreencuestas.txt con el listado.

Punto ciego número 1

La función devuelve un texto con el resultado de la descarga. Ese texto se guarda en RSULTADO y se envía a dbms_output, que en una ejecución programada no lo lee nadie. Si la descarga falla, el procedimiento continúa como si nada. No hay forma de enterarse por esta vía.

Paso 2 — Del disco a DATA_JSON

insertar_json es el corazón del proceso y donde se produce el error visible. Son cuarenta y cinco líneas sin una sola cláusula de manejo de excepciones.

RNIENTREVISTA.insertar_json — cuerpo completo, anotado
procedure insertar_json is
l_clob clob;  V1 VARCHAR2(32767);  V0 VARCHAR2(32767);
F1 UTL_FILE.FILE_TYPE;  F0 UTL_FILE.FILE_TYPE;
BEGIN
F0 := UTL_FILE.FOPEN('ENCUESTAS_DIR','nombreencuestas.txt','R',32767);  ← ORA-29283 AQUÍ
   loop BEGIN
     UTL_FILE.GET_LINE(F0,V0);
     INSERT INTO ENCUESTAStxt VALUES(V0);  -- bitácora del listado
     COMMIT;
     F1 := UTL_FILE.FOPEN('ENCUESTAS_DIR',SUBSTR(V0,50),'R',32767); ← nombre por posición fija
     EXCEPTION WHEN No_Data_Found THEN EXIT; END;

      Loop
          BEGIN
          UTL_FILE.GET_LINE(F1,V1);
          l_clob := l_clob || convert(V1, 'WE8MSWIN1252', 'utf8'); ← conversión de juego de caracteres
          EXCEPTION WHEN No_Data_Found THEN EXIT; END;
      end loop;
      IF UTL_FILE.IS_OPEN(F1) THEN
           insert into data_json values(0,SUBSTR(V0,50),l_clob,sysdate,0);
           commit;
           l_clob := '';
      end if;
      UTL_FILE.FCLOSE(F1);
      UTL_FILE.fremove ('ENCUESTAS_DIR', SUBSTR(V0,50));  ← borra el archivo tras leerlo
   end loop;
   UTL_FILE.FCLOSE(F0);
END;

El detalle que explica el resto del documento: nombreencuestas.txt no es una lista de nombres, sino la salida cruda de un ls -l del FTP. Por eso el nombre del archivo se extrae con SUBSTR(V0,50), es decir, a partir del carácter 50 de la línea. Así se ve una fila real, guardada en ENCUESTASTXT:

Una línea de nombreencuestas.txt, tal como queda registrada
-rw-r--r-- 1 ftp ftp    116790 Oct 05 19:25 YKDURANGOG_25_09_2023_10_51_41949259166.txt
                                             └─ desde aquí (carácter 50) se lee el nombre

Qué pasó el 16 de agosto

La secuencia está completa en el registro del scheduler del 65:

  1. A las 07:03 alguien lanzó el proceso a mano, fuera de su horario.
  2. Corrió 10 horas y 16 minutos y cargó 4 archivos —los últimos que entraron a la base: MCGIRALDOGI, LNGUZMANQ, KINDABURD y ALMAZOE.
  3. Terminó con ORA-01014: ORACLE shutdown in progress. La base se estaba apagando.
  4. A las 18:20 de ese mismo día, la corrida programada ya falló con ORA-29283, y desde entonces falla todos los días en segundos.

El diagnóstico más probable —y el más frecuente en Oracle sobre Windows— es que F: sea una unidad de red o un recurso compartido que no sobrevive al reinicio del servicio: la cuenta con la que arranca Oracle pierde el mapeo y la carpeta deja de existir para la base, aunque siga existiendo para cualquier persona que entre al servidor. La instancia registra un arranque posterior el 22 de agosto a las 21:08, lo que confirma que hubo más de un reinicio en el periodo.

Lo que falta confirmar, y no se puede desde la base

Quedan dos hipótesis compatibles con la evidencia, y se distinguen con una revisión de sistema operativo, no con SQL:

  • En BD-MODELO-19C: ¿existe F:\Encuestas y la ve la cuenta de servicio de Oracle?
  • En el FTP: ¿hay archivos en /EncuestasACargar1 en este momento?

Si F: está caída, se restaura el acceso y todo lo represado entra en la corrida siguiente. Si F: está bien y el FTP está vacío, el corte es más arriba: nadie está copiando de /Encuestas a /EncuestasACargar1, o la APK dejó de subir.

La ventana de 30 días

SP_ADD_ENCUESTAS_MOVIL filtra con WHERE usu_fechacreacion >= SYSDATE - 30. Un archivo que quede represado más de un mes entra a la base y jamás se procesa, sin error y sin traza. Es el mecanismo por el que se perdieron las 56 encuestas de abril y mayo: estuvieron dos y tres meses en el FTP antes de ser recogidas.

Esto tiene consecuencia inmediata sobre cualquier plan de recuperación: volver a subir archivos antiguos al FTP produciría cero filas, en silencio, y todos concluirían que la recuperación funcionó.

La reinserción múltiple

Entre el 22 y el 28 de julio, los mismos 57 archivos entraron a DATA_JSON del 65 ocho días seguidos. El proceso no lleva registro de lo ya consumido: los archivos solo dejan de reingresar cuando una persona los borra del FTP. Los cuatro nombres repetidos que el informe de QA identificó del 12 al 16 de agosto son la cola de este mismo fenómeno.

El canal offline lleva meses sin entregar

Conviene poner el corte en escala. El estado CERRADA_APP_MOVIL en GIC_HOGAR vale 106 hogares, exactamente el mismo número medido en mayo, julio y agosto de 2026, mientras la base creció decenas de miles de hogares. En el mismo periodo, la operación en línea registra entre 400 y 590 hogares por día y de 130 a 180 encuestadores activos.

Es decir: la caracterización no se detuvo. Se detuvo el canal sin conexión, y su deterioro es anterior a agosto.

El segundo informe: la transferencia 65 → 9

El informe del 12 de agosto reporta una pérdida silenciosa del 24,5 % entre DATA_JSON del 65 y del 9, y la atribuye a colisiones de ID entre secuencias independientes. Se validó punto por punto contra producción. La medición se reproduce; la causa raíz no se sostiene, y en el camino aparecieron dos filtros de descarte que no estaban identificados.

Ejecutando su consulta sobre la misma ventana (13 de julio a 12 de agosto) se obtiene 539 / 404 / 135, prácticamente idéntico a sus 535 / 404 / 131. El método es sólido.

La colisión de ID no es la causa

Los hechos que sustentan la hipótesis son ciertos: los ID 40735 y 40755 del 65 están ocupados en el 9 por archivos de 2024, y DATA_JSON no tiene clave primaria ni única sobre ID. Pero el código muestra que ese ID nunca se usa.

IMP_65_FT_IMPORT_JSON — el INSERT no incluye la columna ID
INSERT INTO rnientrevista.data_json (
    nombre_archivo, valor, fecha_inserccion_registro, procesado)   ← sin ID
VALUES (vnombre_archivo, vcolum_clob, vfecha_inserccion_registro, 1);
Y un disparador reasigna el ID en cada inserción
TRIGGER TG_data_json_id_seq
BEFORE INSERT ON rnientrevista.data_json FOR EACH ROW
BEGIN
  :new.id := rnientrevista.data_json_id_seq.nextval;   ← siempre secuencia local
END;

El ID del 9 siempre lo pone la secuencia local, sin importar qué traiga el origen. Las coincidencias son casualidad: dos secuencias independientes que en cinco años llegaron a rangos parecidos.

La prueba que lo cierra

De los 11 archivos que se perdieron, los 11 tenían su ID de origen ocupado en el 9. Pero de los 77 que sí llegaron, los 77 también lo tenían ocupado. Si la colisión fuera la causa, no habría llegado ninguno.

El descarte por nombre está en los dos procedimientos

El informe lo ubica solo en FT_IMPORT_JSON. También está, con la misma forma, en IMP_65_FT_IMPORT_JSON:

IMP_65_FT_IMPORT_JSON — validación por nombre
SELECT COUNT(*) INTO v_count FROM rnientrevista.data_json l
 WHERE l.nombre_archivo = vnombre_archivo;

IF v_count = 0 THEN   INSERT ... ;   v_update := 1;
ELSE                 v_update := 3;   ← "ya existía": ni inserta ni avisa
END IF;

Esto resuelve además una incógnita abierta: PROCESADO = 3 significa «descartado porque el nombre ya existía». Hay 307 filas así en el 65 y 219 en el 9.

Dos filtros de descarte que no estaban identificados

El cursor de FT_IMPORT_JSON —el paso interno del servidor 9— trae dos condiciones adicionales que eliminan filas sin pasar siquiera por el manejo de errores, de modo que no dejan rastro ni en DATA_JSON_FAIL:

ENTREVISTA.FT_IMPORT_JSON — el cursor
FROM rnientrevista.data_json t
WHERE t.fecha_inserccion_registro >= SYSDATE - 200   ← ventana de 200 días
  AND t.valor IS JSON                              ← si no parsea, nunca se selecciona
  AND NVL(t.procesado,0) = 0
  • IS JSON — un archivo cuyo contenido no sea JSON válido queda en PROCESADO = 0 para siempre. Es especialmente relevante porque insertar_json aplica convert(V1,'WE8MSWIN1252','utf8'), que altera cualquier carácter fuera de Latin-1, y porque el cifrado AES entró al flujo el 23 de julio de 2026.
  • Ventana de 200 días — lo más antiguo se abandona. Hay 22 filas represadas en PROCESADO = 0, la más vieja del 28 de octubre de 2025, ya fuera de esa ventana.

El CLOB no viaja bien por el dblink

IMP_65_FT_IMPORT_JSON materializa el CLOB remoto con una subconsulta escalar —el propio código lo comenta como «Materializar CLOB localmente»—. Al intentar reproducirlo, Oracle responde:

Al operar sobre el CLOB remoto
ORA-22992: cannot use LOB locators selected from remote tables

Es la operación más frágil de todo el traslado y es la mejor candidata para explicar los once archivos que quedaron marcados como transferidos sin existir en ninguna tabla. No se aisló fila por fila: se deja señalado como el punto a instrumentar.

Sobre la ausencia de restricciones

La consulta a ALL_CONSTRAINTS con CONSTRAINT_TYPE IN ('P','U') devuelve vacío, y eso es correcto. Pero sí existe unicidad, implementada como índice y no como restricción, por lo que esa consulta nunca la muestra:

Qué queda abierto

Los once archivos perdidos no están en ENTREVISTA.DATA_JSON, ni en DATA_JSON_FAIL, ni en GIC_ENCUESTA_MOVIL. Desaparecieron sin dejar registro, y DATA_JSON_ERROR_LOG —que debía capturarlos— está vacía. Aislar la falla exacta requiere instrumentar una corrida controlada del traslado, con registro por fila. Es el trabajo que sigue.

Cómo mejorarlo

Ordenado por urgencia y por costo. Los cuatro primeros puntos son de días; los tres últimos son decisiones de fondo.

01
Restablecer F:\Encuestas en el 65

Verificar que la carpeta existe y que la cuenta de servicio de Oracle la ve. Si es una unidad mapeada, reemplazarla por una ruta UNC persistente para que sobreviva a los reinicios. Es la reparación del incidente.

Administrador del servidor 65
02
Dejar de borrar /EncuestasACargar1 a las 24 horas

Es la recomendación del informe de QA y es correcta: esa ventana nunca garantizó que el archivo se hubiera procesado. Conservar todo hasta que exista una confirmación de carga verificable.

Operación
03
Alarma sobre el registro de corridas del 65

Este job lleva once días fallando en un segundo y la evidencia estaba disponible desde la primera noche. Una consulta diaria a ALL_SCHEDULER_JOB_RUN_DETAILS con aviso por correo convierte once días de pérdida en una hora.

Base de datos
04
Encender el registro de los jobs del .9

Los cinco jobs de la cadena en el .9 tienen LOGGING_LEVEL = OFF. No existe historial de ejecución: el FAILURE_COUNT que se consulta es un contador acumulado desde 2021, no una bitácora. Encenderlo es un cambio reversible y sin riesgo, y es lo que permitiría auditar la cadena completa.

Base de datos
05
Que insertar_json no pierda el lote entero por un archivo

Hoy no tiene manejo de excepciones: el primer archivo que falle aborta el procesamiento de todos los demás. Y como borra cada archivo apenas lo lee, lo ya procesado desaparece y lo pendiente queda sin tocar. Un bloque por archivo, con registro del que falló en DATA_JSON_ERROR_LOG —que existe desde mayo de 2026 y sigue con cero filas—, resuelve las dos cosas.

Desarrollo del legacy
06
Dejar de identificar los archivos por su posición en un ls -l

SUBSTR(V0,50) depende del ancho de la columna de tamaño, que ls calcula según el archivo más grande del listado. Un archivo suficientemente grande desplaza todos los nombres y hace fallar el lote completo. Conviene listar el directorio local en lugar de interpretar la salida del FTP.

Desarrollo del legacy
07
Revisar la ventana de 30 días y el control de duplicados

La ventana descarta en silencio todo lo capturado hace más de un mes; debería ser un parámetro, no una constante, y lo que quede fuera debería registrarse. En paralelo, el control de duplicados por nombre de archivo —dos índices únicos añadidos en mayo de 2026— convierte una colisión de nombres en un lote perdido, porque no hay manejo de excepciones que lo absorba.

Desarrollo del legacy · decisión funcional
08
Instrumentar el traslado 65 → 9 fila por fila

Es el único punto donde hoy no sabemos qué pasa: once archivos marcados como transferidos no existen en ninguna tabla y DATA_JSON_ERROR_LOG está vacía. Una corrida controlada que registre cada fila —incluidos los descartes por IS JSON y por ventana de 200 días, que hoy no pasan por el manejo de errores— aislaría la falla en una sesión.

Base de datos · prioritario
09
Que ningún descarte sea silencioso

Hoy hay al menos cuatro formas de que un archivo desaparezca sin dejar rastro: nombre repetido (PROCESADO = 3), contenido que no parsea como JSON, antigüedad mayor a 200 días, y captura de más de 30 días en el procesamiento posterior. Ninguna genera alerta. Cada una debería dejar una fila con su motivo, y esas filas deberían reportarse a la operación, no quedarse en la base.

Desarrollo del legacy
10
Sustituir el eslabón por un cargador con bitácora

A mediano plazo, el paso FTP → base no debería vivir como Java dentro de Oracle leyendo la salida de un ls. Un cargador externo que registre qué hizo con cada archivo, que no borre el origen hasta confirmar la escritura y que verifique con una consulta lo que acaba de insertar, elimina de un golpe los seis modos de falla descritos aquí.

Arquitectura

Precisiones sobre el informe de QA

El informe del 26 de agosto identificó correctamente que la cadena estaba cortada, fechó el corte con precisión y documentó el método de forma reproducible, que es lo que permitió llegar hasta acá. Tres precisiones sobre el diagnóstico:

  • El job señalado no es el que falla. El JOB_PCD_FN_FTP_PC_IJ deshabilitado desde 2024 es una copia inactiva en el .9. El homónimo del 65 está encendido y es el que opera. El inventario de jobs se hizo sobre ALL_SCHEDULER_JOBS sin dblink, que solo describe el .9.
  • El paso 3 sí está automatizado. No requiere que nadie lo ejecute a mano. La ejecución manual del 16 de agosto fue puntual, y de hecho coincidió con el apagado de la base que originó el corte.
  • «El resto de la cadena funciona» es cierto, pero no por la razón indicada. Un FAILURE_COUNT bajo no acredita salud en esta base: los procedimientos confirman internamente y capturan las excepciones sin relanzarlas, de modo que un job puede terminar en SUCCEEDED sin haber escrito una fila. Lo que sí acredita salud es el cruce entre corridas y filas efectivamente insertadas, que es como se ubicó el corte.

Sobre las once encuestas de Venadillo: antes de darlas por perdidas conviene barrer toda la ruta de preparación —DATA_JSON, GIC_ENCUESTA_MOVIL, GIC_PERSONAS_ENCUESTA, DATA_JSON_FAIL, los históricos— y no solo GIC_PERSONA. Hay estados de hogar que contienen trabajo de campo terminado y que ningún reporte muestra; si las encuestas están ahí, se recuperan sin volver al municipio.

Cómo reproducir este diagnóstico

Todas las consultas son de solo lectura y se ejecutan desde el .9. El sufijo @DBL_RNIENTREVISTA las dirige al 65.

1 · El job real y su programación
SELECT owner, job_name, enabled, state, repeat_interval,
       last_start_date, run_count, failure_count
FROM   all_scheduler_jobs@DBL_RNIENTREVISTA
WHERE  job_name = 'JOB_PCD_FN_FTP_PC_IJ';
2 · Corridas y error exacto
SELECT status, actual_start_date, run_duration, error#,
       SUBSTR(additional_info,1,200)
FROM   all_scheduler_job_run_details@DBL_RNIENTREVISTA
WHERE  job_name = 'JOB_PCD_FN_FTP_PC_IJ'
ORDER BY actual_start_date DESC;
3 · Cruce entre corridas y filas realmente cargadas
SELECT TO_CHAR(d.actual_start_date,'YYYY-MM-DD') dia, d.status, d.run_duration,
       (SELECT COUNT(*) FROM rnientrevista.data_json@DBL_RNIENTREVISTA j
         WHERE TRUNC(j.fecha_inserccion_registro) = TRUNC(d.actual_start_date)) filas
FROM   all_scheduler_job_run_details@DBL_RNIENTREVISTA d
WHERE  d.job_name = 'JOB_PCD_FN_FTP_PC_IJ'
ORDER BY d.actual_start_date DESC;
4 · Estado de lo pendiente y de lo fallido
SELECT procesado, COUNT(*), MIN(fecha_inserccion_registro), MAX(fecha_inserccion_registro)
FROM   entrevista.data_json GROUP BY procesado;

SELECT COUNT(*) FROM entrevista.data_json_fail;
SELECT COUNT(*) FROM rnientrevista.data_json_error_log;
5 · El código, tal como está hoy en producción
SELECT line, text FROM all_source@DBL_RNIENTREVISTA
WHERE  name IN ('PCD_FN_FTP_PC_IJ','INSERTAR_JSON','FN_EXEC_FTP_JSFULL_WRAP')
ORDER BY name, line;

Documento elaborado a partir de consultas SELECT ejecutadas el 27 de agosto de 2026 contra RNIENTREVISTA@30.0.1.9/ENTREVISTARN y, por el dblink DBL_RNIENTREVISTA, contra BD-MODELO-19C. No se modificó ningún dato, procedimiento ni job. Las dos verificaciones pendientes —la carpeta F:\Encuestas en el 65 y el contenido de /EncuestasACargar1— corresponden al sistema operativo y al servidor FTP, fuera del alcance de una consulta a la base.
